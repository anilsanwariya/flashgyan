# Architecture

> How FlashGyan works and where code goes. Keep this up to date when the structure changes.

## Stack

| Layer | Choice |
| --- | --- |
| Builder and host | Lovable (builds from this repo; serves on Cloudflare Workers through Nitro) |
| Framework | TanStack Start (React 19, file-based routes, server functions, server-side rendering) |
| Language | TypeScript |
| Styling | Tailwind CSS 4 with shadcn/ui components (`src/components/ui`) |
| Database, auth, files | Supabase through Lovable Cloud: PostgreSQL with Row Level Security, Auth (admins only), Storage |
| Telegram bot | One Supabase Edge Function (Deno): `supabase/functions/telegram-demo-bot` |
| AI text | Claude (`claude-sonnet-5`) through the Anthropic API |
| AI search | Google `gemini-embedding-001` embeddings (1536 dimensions) plus PostgreSQL full-text search |
| Other services | Tavily (news search), LlamaParse (PDF reading), Cloudflare Browser Rendering (PDFs and image cards) |

## How a request flows

```
Student's browser / Telegram Mini App
        │
        ▼
TanStack Start on Cloudflare ──► page rendered on the server (SEO, link previews)
        │
        ▼
Server function (src/lib/*.functions.ts) or API route (src/routes/api.*.ts)
        │                          │
        │ public reads: anon key   │ admin work: assertAdmin(), then service-role client
        ▼                          ▼
             Supabase PostgreSQL (RLS on every table) and Storage
        │
        ▼
AI and outside services (Claude, Gemini embeddings, Tavily, LlamaParse, Cloudflare)

Telegram ──webhook──► Edge Function telegram-demo-bot ──► same database, same AI code
pg_cron ──every minute──► /api/ca/tick and the bot's ?task=broadcast
```

## Folders

```
src/
  routes/                 File-based pages. A file name is its URL:
                          atlas.place.$key.tsx -> /atlas/place/:key
    api.*.ts              Server-only HTTP endpoints (streaming SAATHI, cron ticks, previews)
    _authenticated/       Admin area; requires sign-in
    sitemap[.]xml.ts      Generated sitemap
  components/
    ui/                   shadcn/ui building blocks. Reuse these; don't restyle them.
    <area>-*.tsx          Feature UI by area: atlas-, ca- (current affairs), exam-,
                          flash- (card studio), gk-, ig- (Words in the News), notes-,
                          saathi-, bot-
  lib/
    *.functions.ts        Server functions: the only way the browser reaches the server.
                          Validate input with zod here.
    *.server.ts           Server-only logic and database work, loaded by server functions
                          with `await import(...)`. Never import these from components.
    *.ts                  Shared pure logic (parsing, formatting, scoring). Safe anywhere.
  integrations/supabase/  Generated by Lovable. Don't edit. types.ts mirrors the live database.
  hooks/                  React hooks
  styles.css              Design tokens (see DESIGN.md)
supabase/
  migrations/             SQL migrations from before 11 Oct 2026 and from outside Lovable
                          (Lovable's own are in drizzle/migrations; see Database changes)
  functions/
    telegram-demo-bot/    The Telegram bot (webhook and scheduled tasks)
    _shared/              Code shared by the bot AND the website: saathi-core (all AI calls),
                          ca-* (current affairs), ras-syllabus, telegram helpers.
                          Must run in both Deno and Node: no Node-only or Deno-only APIs
                          except behind checks.
public/                   Static files: manifest, service worker (sw.js), offline page, icons
scripts/                  One-off build scripts (map data)
e2e/                      Browser tests (Playwright) with a fake Supabase and sample data;
                          own package.json, not part of the app build
.github/workflows/        GitHub checks on every pull request and push to main
docs/                     Project documentation (this folder)
```

## Key patterns

- **Who is the user?** Students have no accounts. Study progress lives in the browser
  (`localStorage`, `sessionStorage`). Admins sign in with Supabase Auth, password plus an
  authenticator-app code; admin rights come from the `user_roles` table and are checked on
  the server by `assertAdmin()` (which includes `requireAdminMfa()`) in every admin
  function. Telegram Mini App users are verified from Telegram's signed
  `initData` (`telegram-init-data.server.ts`).
- **Reading data:** public pages read through server functions using the public (anon)
  key, so Row Level Security still applies. Admin functions use the service-role client
  (`client.server.ts`) only after `assertAdmin()`.
- **Images:** study images are in private buckets; students get signed URLs from server
  functions. Buckets: `flashcard-images`, `mcq-images`, `home-banners`, `bot-media`,
  `ca-clips`, `ca-magazines`, `exam-papers`.
- **AI:** every AI text call goes through `saathiComplete` in `_shared/saathi-core.ts`,
  which calls Claude, applies prompt caching and records tokens in `ai_usage`. Keep a
  prompt's first system message identical between calls so the cache works (see AGENTS.md).
  Background jobs nobody waits on can send their calls as a Message Batch
  (`saathiBatchCreate` / `saathiBatchGet` / `saathiBatchResults`, half price); a job's
  model and effort are set per job (`ai-jobs.ts`, `bot_settings` key `ai_jobs`). The atlas
  translation does both (ADR-020). Card studio server jobs and the exam upload queue
  batch their existing steps by running each step twice (`ai-batch.server.ts`: capture the
  request, then replay the batch's reply if what it was about is unchanged; ADR-021).
- **SAATHI search:** hybrid search (`match_saathi_hybrid`): embedding similarity plus
  keyword rank, then the model picks the best passages. SAATHI answers only from
  `saathi_knowledge`.
- **Long jobs:** heavy work (magazines, card studio, paper reading) runs as queued jobs
  advanced a step at a time. In the bot, slow AI replies run in `EdgeRuntime.waitUntil`
  after an immediate acknowledgment.
- **Scheduled work:** `pg_cron` with `pg_net` calls `/api/ca/tick` (news collection) and the
  bot's `?task=broadcast` every minute. These schedules are **not** in the migrations: an
  admin runs the SQL shown in Admin → Current affairs (watch sites) and Admin → Telegram
  bot → Connection. Tick endpoints do only work that is already due, so calling them
  without credentials is safe.
- **Rate limits:** public AI endpoints are limited per IP and site-wide
  (`saathi_rate_limits`, `consumeSaathiRateLimit`).
- **Bilingual:** content is stored in English and Hindi. In the atlas, AI-drafted Hindi is
  marked as the AI's until a person checks it.
- **App promotion and SEO:** Play Store links go through `src/lib/app-promo.ts`. Deck
  pages and `sitemap.xml` are rendered on the server for search engines.
- **Atlas district card:** `atlasDistrictOutlineFn` returns the district's topics and counts
  (`factsOutline(shownFacts(...))` in `src/lib/atlas.ts`), and `atlasDistrictPartFn` one
  topic's facts or the Places tab's ("places"). The server works the district out once and
  keeps it with the atlas's other data (5 minutes, cleared by `invalidateAtlas`); offline,
  the same helpers run on the saved pack.
- **Atlas theme pages from the notes:** `src/lib/atlas-notes-themes.ts` turns a subject's
  notes (found by chapter title) into the four pages' data, from their headings and tables
  ("Sakas and Jauhars…", "Fairs month by month › Chaitra", "Mewar School › Nathdwara
  style"); `atlasNotesThemeFn` serves it, cached with the atlas's data.
- **Atlas place photos:** `src/lib/atlas-photos.server.ts` searches the Wikimedia Commons
  API (with a FlashGyan user agent), keeps only freely licensed files, and saves the
  editor's choices in `bot_settings` (`atlas_photos`). `atlasPlace` returns a place's
  photo; the picture is Commons' thumbnail on upload.wikimedia.org.
- **PWA:** `public/sw.js` and `public/offline.html`, registered by `src/lib/pwa.ts`.

## Database changes

The database's history is split across **two folders**. Together they are the full record;
neither is complete on its own.

| Folder | Written by | Contents |
| --- | --- | --- |
| `drizzle/migrations/` | Lovable, since 11 October 2026 (numbered `0000_…`, journal in `meta/_journal.json`) | Lovable's changes, including the security work: private image buckets (`0001`), `is_public` on catalogs and banners (`0002`, `0003`), admin-only SAATHI sources (`0004`) |
| `supabase/migrations/` | Everything before 11 October 2026, and changes made outside Lovable (Claude) | Most tables and features |

- Never edit a migration that has already run; add a new file.
- Changes made **in Lovable** go to `drizzle/migrations/` (Lovable does this itself).
- Changes made **outside Lovable** go to `supabase/migrations/`. File names there must sort
  after the last file (now `20261225…`, although written in November 2026), so name new
  files after the latest one, not by today's date.
- **Lovable does not run migrations added from outside it.** After merging one, the owner
  runs its SQL by hand in Lovable's SQL editor (confirmed with
  `20261225090000_practice_sessions.sql` on 4 November 2026). So:
  - write it so it is safe to run more than once (`IF NOT EXISTS`, `CREATE OR REPLACE`);
  - make the code work before it runs (detect the missing table and do nothing, or show
    "Run the migration …"), because the site goes live before the SQL is run;
  - say in the pull request that the SQL must be run after merging.
- Every new table needs `ENABLE ROW LEVEL SECURITY` and explicit policies.
- `src/integrations/supabase/types.ts` (generated by Lovable) mirrors the live schema.

## Deployment

| What | How | Check |
| --- | --- | --- |
| Website | Merge to `main`; Lovable syncs and publishes | Open the live site |
| Database | Lovable applies its own (`drizzle/migrations/`). Others: run the file's SQL in Lovable's SQL editor after merging | The feature's admin page no longer asks for the migration |
| Telegram bot | Ask Lovable to redeploy `telegram-demo-bot`. **Merging does not redeploy it.** | `…/functions/v1/telegram-demo-bot` shows `ok`; Admin → Telegram bot → Connection |
| Scheduled jobs | Run the SQL from the admin panels once | Lovable Cloud → Database: `select * from cron.job;` |
